# ADR-045: Bootstrap FreeSWITCH deployment credentials for Oduflow

## Status

Accepted.

## Context

The FreeSWITCH deployment has two service-to-Odoo trust boundaries:

- `freeswitch_webhook_token`, passed to the `fs` container as
  `FS_WEBHOOK_TOKEN`;
- `firewall_service_token`, passed to the `firewall` container as
  `AGENT_TOKEN`.

Both values were already generated by separate installation helpers, but the
deployment workflow treated them as values an operator had to copy from the
settings form. That is unsuitable for Oduflow-managed services: the fields are
masked in the UI, while an Oduflow agent can read the stored admin-only values
through an Odoo shell and pass them directly to service environment variables.

The `connect.settings` singleton normally exists before
`connect_freeswitch` is installed. Field defaults alone therefore do not
guarantee that provider-specific secrets are populated when the provider is
added to an existing database.

## Decision

- `connect_freeswitch` exposes one idempotent deployment bootstrap helper that
  ensures both service tokens and the firewall agent singleton exist.
- The module post-install hook invokes this helper before any external license
  refresh, so transient license-service failures cannot prevent credential
  creation.
- The current per-series post-migration invokes the same helper. This repairs
  databases where either value was cleared or where a previous installation
  did not complete its bootstrap.
- Bootstrap is missing-only. Existing token values are never rotated or
  overwritten.
- Tokens remain admin-only protected settings. Oduflow reads them with `sudo()`
  only while creating or updating the two services and must not print them in
  summaries, commit them, or store them in deployment files.
- The `fs` service receives `freeswitch_webhook_token` as
  `FS_WEBHOOK_TOKEN`; the `firewall` service receives
  `firewall_service_token` as `AGENT_TOKEN`.

## Consequences

- Installing or upgrading `connect_freeswitch` leaves the database ready for
  automated service deployment without an administrator inventing secrets.
- Re-running installation, migration, or deployment is safe because existing
  credentials are stable.
- Rotating either service token remains an explicit operational action and
  requires updating the corresponding service environment in the same
  maintenance window.
- Agent deployment instructions are part of the security contract: an agent
  must inspect an existing service before updating it and must preserve all
  unrelated environment variables and runtime privileges.
