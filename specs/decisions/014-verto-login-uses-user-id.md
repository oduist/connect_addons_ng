# ADR-014: Verto login uses res.users.id instead of res.users.login

**Status:** Accepted
**Date:** 2026-04-29

## Context

The Verto WebRTC softphone in `connect_freeswitch` authenticates against
FreeSWITCH `mod_verto` over a WebSocket using a JSON-RPC `login` method.
Until this decision, both the JS client (`connect_freeswitch/static/src/js/verto_client.js`)
and the server (`get_webrtc_config` in `connect_freeswitch/models/settings.py`
and `connect_freeswitch/controllers/webrtc.py`) used `res.users.login` as
the Verto username. The FreeSWITCH XML directory generated by
`connect_freeswitch/controllers/freeswitch_xml.py` keyed WebRTC users by
`user.login` to match.

`mod_verto` parses the JSON-RPC `login` parameter as `<user>@<realm>`:
it splits on the first `@` and uses the right-hand part as the SIP realm
to look up a directory `<domain name="…">` known to FreeSWITCH (the
configured `freeswitch_domain`).

For any deployment where `res.users.login` is an email — the standard
case in production installs that use SSO or email-based logins — the
JS client sends, e.g., `c.rochat@reiso.org`. `mod_verto` then asks the
directory for user `c.rochat` in domain `reiso.org`, fails to find that
domain, and rejects the login with:

```
mod_verto.c:1061 Login incorrect for user: c.rochat domain: reiso.org
```

The softphone widget lands in the `error` state and is unusable. This
was reported as issue #53 (BLOCKER): every email-login user in
production was unable to register the WebRTC softphone. The issue was
only visible to admin operators with non-email logins; impersonating
("Log in as") an email-login user surfaced the bug instantly.

## Options

1. **Strip `@…` on the client and match the local-part on the server.**
   Keep human-readable usernames. Risk: collisions when two users share
   the same local-part across email domains
   (`alice@x.com` and `alice@y.com` both become `alice`).
2. **Add a dedicated `webrtc_username` field on `connect.user`.**
   Most flexible (admin-editable, audit-trail-friendly), but requires a
   schema field, view tweak, and migration script for marginal user
   benefit. Also pushes a new piece of mandatory configuration onto
   admins.
3. **Use the numeric `res.users.id` as the Verto username on both sides.**
   Server-controlled, guaranteed unique by Postgres, decoupled from
   email/login changes, never contains `@`. No schema change, no
   migration. The id is already exposed to other parts of the stack
   (`odoo_user_id` directory variable, click-to-call URIs) so this is
   not a new conceptual primitive.

## Decision

Use **option 3: numeric `res.users.id` (string-encoded) as the Verto
login string.**

### Affected paths (all touched in this ADR's accompanying patch)

- `connect_freeswitch/models/settings.py` (`get_webrtc_config`):
  returns `'login': str(user.id)`.
- `connect_freeswitch/controllers/webrtc.py` (`get_webrtc_config`,
  legacy duplicate JSON-RPC route): same change.
- `connect_freeswitch/controllers/freeswitch_xml.py`
  (`_get_user_xml`): the WebRTC lookup branch matches by id
  (`('user', '=', int(user))`) instead of `user.login`. Guarded by
  `user.isdigit()` so a SIP `auth_user` that looks like an email is
  never accidentally treated as a numeric Verto id.
- `connect_freeswitch/controllers/freeswitch_xml.py`
  (`_directory_for_user_bridge`, `_get_full_directory`): WebRTC
  contacts are keyed by `str(user.id)` and the `verto_contact(...)`
  dial-string uses the same id.
- `connect_freeswitch/models/call.py`: click-to-call a-leg
  (`verto_h_auto_answer=true]user/<id>@<domain>`) and
  `_build_user_bridge` (`user/<id>@<domain>` for the WebRTC contact)
  both use `str(connect_user.user.id)`.
- `connect_freeswitch/static/src/js/verto_client.js`: the existing
  `_appendDomain()` builds `<id>@<freeswitch_domain>` correctly when
  the input has no `@`. A defensive `console.warn` was added in
  `_login()` to surface any future regression where a string with
  `@` slips through.

SIP endpoints continue to authenticate by `auth_user` (the lookup
order in `_get_user_xml` checks `auth_user` first); only the WebRTC
branch changed. Hardphones provisioned with `auth_user='1000'` keep
working unchanged.

### Why not allow either

Accepting both `user.login` and `str(user.id)` simultaneously
on the server side would mean the lookup tries login first, then
falls back to id. That is a transient compatibility mode that
cannot be removed safely once written, and it does not solve the
client-side problem (the client must pick one). Switching cleanly
to id-only is simpler and self-consistent.

### Caller-id implications

Where the previous code fell back to `user.login` for a
caller-id-number (purely cosmetic, never used by FS for routing),
the fallback chain is now `exten_number → name → str(id)`, so a
called party never sees a bare numeric internal id when something
better is available.

## Consequences

- **No database migration.** The login string was never stored; it
  was derived at runtime from `res.users.login`. After deploying
  this fix, any browser session that was logged in with the old
  (email) login will be rejected on the next reconnect and the JS
  client will then re-fetch `get_webrtc_config` and reconnect with
  the new id-based login.
- **FreeSWITCH XML cache.** `mod_xml_curl` caches directory entries.
  After deploying, run `fs_cli -x "xml_locate directory"` once on
  the FreeSWITCH host to invalidate cached entries keyed by the old
  login. New entries for the same user with the new id key will be
  fetched on the next auth challenge.
- **Logs.** FreeSWITCH `mod_verto` will log
  `Login sucessful for user: <numeric-id> domain: <freeswitch_domain>`
  instead of the previous `<login>` form. Operational dashboards or
  log-based alerts that match on the username field need to be
  updated accordingly.
- **No upstream API change.** The JSON-RPC route
  `/connect/webrtc/config` keeps the same shape and field names; only
  the value of `login` changes. No external integration depends on
  the previous value.
- **No effect on Twilio path.** `connect_twilio` does not use Verto.

## Verification

1. Upgrade `connect_freeswitch` to `18.0.1.7.12` (or later).
2. `fs_cli -x "xml_locate directory"` to clear cached directory entries.
3. Open Odoo as a user with an email login (or "Log in as" them).
4. The softphone systray icon transitions to `registered`.
5. FS log shows
   `Login sucessful for user: <res.users.id> domain: <freeswitch_domain>`.
6. Click-to-call originates an a-leg whose Verto contact is
   `user/<id>@<domain>`; the browser softphone rings and auto-answers.
7. Inbound call to the user's extension follows the user-bridge dial
   string and rings the browser softphone.
