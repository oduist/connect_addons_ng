# ADR-016: Verto login uses `<login-local-part><res.users.id>`

**Status:** Accepted (revised 2026-05-17)
**Date:** 2026-04-29 (original), 2026-05-17 (revised)

## Context

The Verto WebRTC softphone in `connect_freeswitch` authenticates against
FreeSWITCH `mod_verto` over a WebSocket using a JSON-RPC `login` method.
`mod_verto` parses the `login` parameter as `<user>@<realm>`: it splits
on the first `@` and uses the right-hand part as the SIP realm to look
up a directory `<domain name="…">` known to FreeSWITCH (the configured
`freeswitch_domain`).

Until the original version of this ADR, both the JS client
(`connect_freeswitch/static/src/js/verto_client.js`) and the server
(`get_webrtc_config` in `connect_freeswitch/models/settings.py` and
`connect_freeswitch/controllers/webrtc.py`) used `res.users.login` as
the Verto username, and the FreeSWITCH XML directory generated by
`connect_freeswitch/controllers/freeswitch_xml.py` keyed WebRTC users
by `user.login` to match.

For any deployment where `res.users.login` is an email — the standard
case in production installs that use SSO or email-based logins — the
JS client sent, e.g., `c.rochat@reiso.org`. `mod_verto` then asked the
directory for user `c.rochat` in domain `reiso.org`, failed to find
that domain, and rejected the login with:

```
mod_verto.c:1061 Login incorrect for user: c.rochat domain: reiso.org
```

The softphone widget landed in the `error` state and was unusable.
This was reported as issue #53 (BLOCKER): every email-login user in
production was unable to register the WebRTC softphone.

The first remediation (PR #54) switched the login to the bare numeric
`str(res.users.id)`. That fixed the auth, but two operational problems
surfaced quickly:

1. **Poor debuggability.** FreeSWITCH logs show
   `Login sucessful for user: 42 domain: …` — to identify the actual
   user, an operator must open Odoo and look up `res.users.id`.
2. **No semantic anchor.** A bare numeric id reads identically to a
   SIP extension number and gives support no clue about which Odoo
   user is registering.

## Options

1. **Strip `@…` on the client and match the local-part on the server.**
   Keep human-readable usernames. Risk: collisions when two users share
   the same local-part across email domains
   (`alice@x.com` and `alice@y.com` both become `alice`).
2. **Add a dedicated `webrtc_username` field on `connect.user`.**
   Most flexible (admin-editable, audit-trail-friendly), but requires a
   schema field, view tweak, and migration script for marginal user
   benefit. Pushes a new piece of mandatory configuration onto admins.
3. **Use the numeric `res.users.id` as the Verto username.**
   Server-controlled, guaranteed unique by Postgres, decoupled from
   email/login changes, never contains `@`. No schema change, no
   migration. *Chosen in PR #54*; later rejected because of poor
   debuggability (see Context).
4. **Use `<login-local-part><res.users.id>`, e.g. `litnimax42`.**
   Combines the readability of option 1 with the uniqueness of option
   3. Local part comes from `res.users.login.split('@')[0]`; the
   trailing id makes the login globally unique even when local parts
   collide across email domains. Never contains `@` (the `@` is
   stripped). No schema change, no migration.

## Decision

Adopt **option 4: `<login-local-part><res.users.id>`** as the Verto
login string on both sides (server-emitted to the JS client, and
server-parsed for the XML directory lookup).

### Helper API

`connect.user` exposes two helpers
(`connect_freeswitch/models/fs_user.py`) so the formula lives in one
place:

```python
def _get_verto_login(self):
    """Return '<login-local><res.users.id>' for this connect.user."""

@api.model
def _resolve_verto_login(self, login_str):
    """Reverse: '<local><id>' -> res.users (verifies local matches)."""
```

The reverse parser uses `^(.+?)(\d+)$` (non-greedy prefix + greedy
trailing digits) and then verifies that the captured local part
matches `user.login.split('@')[0]`, which rejects false matches when
a user's own login happens to end in digits.

### Affected paths

- `connect_freeswitch/models/fs_user.py`: defines `_get_verto_login`
  and `_resolve_verto_login`.
- `connect_freeswitch/models/settings.py` (`get_webrtc_config`):
  returns `'login': connect_user._get_verto_login()`.
- `connect_freeswitch/controllers/webrtc.py` (`get_webrtc_config`,
  legacy duplicate JSON-RPC route): same change.
- `connect_freeswitch/controllers/freeswitch_xml.py` (`_get_user_xml`):
  the WebRTC lookup branch uses
  `ConnectUser._resolve_verto_login(user)` to map the incoming login
  back to a `res.users`.
- `connect_freeswitch/controllers/freeswitch_xml.py`
  (`_directory_for_user_bridge`, `_get_full_directory`): WebRTC
  contacts are keyed by `_get_verto_login()` and the
  `verto_contact(...)` dial-string uses the same value.
- `connect_freeswitch/models/call.py`: click-to-call a-leg
  (`verto_h_auto_answer=true]user/<login>@<domain>`) and
  `_build_user_bridge` (`user/<login>@<domain>`) both use
  `_get_verto_login()`.
- `connect_freeswitch/static/src/js/verto_client.js`: the existing
  `_appendDomain()` already handles any value without `@`. The
  defensive `console.warn` in `_login()` keeps watching for `@` —
  only its comment was updated to describe the new format.

SIP endpoints continue to authenticate by `auth_user` (the lookup
order in `_get_user_xml` checks `auth_user` first); only the WebRTC
branch changed. Hardphones provisioned with `auth_user='1000'` keep
working unchanged; the reverse parser correctly returns an empty
recordset for `'1000'` (no prefix part) so it would not collide even
if the order changed.

### Why not accept both old formats simultaneously

Accepting both `str(user.id)` and `'<local><id>'` on the server side
would mean the lookup tries one, then falls back. That is a transient
compatibility mode that cannot be removed safely once written, and
does not help the JS client (it must pick one). Switching cleanly is
simpler and self-consistent. Active browser sessions reconnect
automatically with the new login on the next refetch of
`get_webrtc_config`.

### Caller-id implications

Where the previous code fell back to the Verto login string for
caller-id-number (purely cosmetic, never used by FS for routing),
the fallback chain is now `exten_number → name → verto_login`,
which now reads as e.g. `litnimax42` instead of a bare `42`.

## Consequences

- **No database migration.** The login string is derived at runtime
  from `res.users.login` + `res.users.id`. After deploying this
  revision, browser sessions on the previous (bare-id) login will be
  rejected on the next reconnect, and the JS client will re-fetch
  `get_webrtc_config` and reconnect with the new login.
- **FreeSWITCH XML cache.** `mod_xml_curl` caches directory entries.
  After deploying, run `fs_cli -x "xml_locate directory"` once on the
  FreeSWITCH host to invalidate cached entries keyed by the old
  numeric login. New entries for the same user under the new key will
  be fetched on the next auth challenge.
- **Logs.** FreeSWITCH `mod_verto` will log
  `Login sucessful for user: <local><id> domain: <freeswitch_domain>`
  (e.g. `litnimax42`) instead of the previous bare numeric id.
  Operational dashboards or log-based alerts that match on the
  username field need to be updated accordingly.
- **No upstream API change.** The JSON-RPC route
  `/connect/webrtc/config` keeps the same shape and field names; only
  the value of `login` changes.
- **No effect on Twilio path.** `connect_twilio` does not use Verto.

## Verification

1. Upgrade `connect_freeswitch` to `18.0.1.7.13` (or later).
2. `fs_cli -x "xml_locate directory"` to clear cached directory
   entries.
3. Open Odoo as a user with an email login (or "Log in as" them).
4. The softphone systray icon transitions to `registered`.
5. FS log shows
   `Login sucessful for user: <local><id> domain: <freeswitch_domain>`
   (e.g. `admin1`, `litnimax42`).
6. Click-to-call originates an a-leg whose Verto contact is
   `user/<local><id>@<domain>`; the browser softphone rings and
   auto-answers.
7. Inbound call to the user's extension follows the user-bridge dial
   string and rings the browser softphone.
8. Two users with the same email local part across domains
   (`alice@x.com` id=42, `alice@y.com` id=57) produce distinct
   logins (`alice42`, `alice57`) and both register independently.
